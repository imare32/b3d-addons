# 双摆相空间阵列（Sim Pendulum）

把 **N×N 个理想双摆**摆成一张平面阵列，每格一个初值，逐帧用四阶 Runge–Kutta 推进，
实时画成 Grease Pencil 笔划（扩展 id `sim_pendulum`，Blender 5.2.2 实测）。

两种画法（面板「画法」）：

| 画法 | 一个摆 = | 后端 | 用在哪 |
|---|---|---|---|
| **杆（三笔）** | 下摆 2 点 + 上摆 2 点 + 扣子 1 点 | GP 笔划 | 小 / 中规模（N ≤ ~100），看结构、看分形 |
| **点（一像素一个摆）** | 一个像素 | **图像数据块**（`image.pixels`） | 大规模：N = 512 → 26 万像素，N = 1000 → 100 万 |

杆画法里每个摆画成**三条笔划**，顺序就是绘制顺序：

```
下摆（关节 → 摆锤，等宽、两端圆头）  ← 最下面一层
上摆（悬挂点 → 关节，等宽、两端圆头）← 压在它上面
扣子（关节上的一个圆点）              ← 最上面一层，颜色与下摆一致
```

一条 3 点折线只能给"逐点颜色"，于是从悬挂点到摆锤是**渐变**，两根杆的结构就糊了；
拆成三笔以后每条笔划内部颜色恒定，扣子和下摆同色、上摆另一种颜色，交界处就是一个
"扣住"的接头。N 上百（100² = 一万个摆）时，这些接头连成双摆的分形图案，颜色还会整片
流动 —— 所以配色给了**全色相**一档，把整个色轮都交给相角。

积分有**两个求解器**，面板可切：纯 NumPy（零依赖，缺省自动回退）与可选的 **Taichi GPU**
（装了就自动用；1 万摆 3.4 ms/帧 vs NumPy 8.2 ms）。结果可以落到两种对象上：

| 输出 | 结构 | 逐帧同步 | 用途 |
|---|---|---|---|
| **Grease Pencil**（缺省） | 一个摆 = 三条笔划 / 5 个点 | `foreach_set` 位置 / 逐点半径 / 逐点颜色 / 6 个标量 | 本仓库偏好的画法，同步最快，有扣子 |
| **网格 + 几何节点** | 一个摆 = 5 顶点 / 2 条边，GN 扫成圆管 | 同一份数据（顶点属性） | 只为对照开销，画不出扣子 |

## 快速开始

1. 仓库已注册为本地扩展仓库（见根目录 `README.md`），启用 **Sim Pendulum**；
2. 3D 视图侧栏出现 **Pendulum** 面板（F3 里也有 `sim_pendulum.*` 算子）；
3. 点「构建」——建阵列对象、相空间场、正面正交相机，画面停在第 1 帧；
4. 播放（或点「+1 帧」）：整片摆从同一个姿势散开，慢慢变成一团乱线；
5. 想看分形：把「边长 N」拉到 **100**、配色切到**全色相**，点「场景预设」——
   分辨率会自动给到 3200 px（每世界单位 26 px，N 大时线才不会细成亚像素）。

算子：`sim_pendulum.build`、`sim_pendulum.reset`（回初始阵列，不重建拓扑）、
`sim_pendulum.step`（时间轴 +1 帧）、`sim_pendulum.setup_scene`、
`sim_pendulum.benchmark`（GP 与网格各刷一遍、报每帧同步耗时）、
`sim_pendulum.fix_viewport`、`sim_pendulum.delete`。

颜色只写在属性里，而 Solid 视图默认的「着色颜色 = Material」读的是材质单色 —— 这时线是
**全黑**的。所以「构建」「场景预设」会顺手把 Solid 视图切成 **Attribute**；播放中要是又切
回 Material，面板会亮一条红色提示，点 `sim_pendulum.fix_viewport` 即可。

## 面板参数

三档参数的生效方式不同，面板上也分开摆：

| 分组 | 参数 | 说明 |
|---|---|---|
| 阵列 / 精度 | 边长 N | N×N 个摆（每个摆三条笔划 / 五个点）。16 → 256 个摆；100 → 10000 个摆 / 5 万个点（上限 128） |
| | 初值 | **摆角平面 θ1–θ2**：θ1 沿 X、θ2 沿 Z，角速度全 0；**相空间 θ1–dθ1**：θ2 = 0、dθ2 = 0，纵轴是初角速度 |
| | 间距 | 相邻摆的距离（缺省 2.4）。要比 `l1 + l2` 大，否则上一排的摆会垂进下一排的格子 |
| | 初角速度 | 相空间档位下纵轴的满量程 `±spin_max`（rad/s） |
| | 画法 | **杆（三笔）**：一个摆三笔、逐点半径；**点**：一个摆一个像素。切到点阵会自动把输出切成图像、N 设成 512（没 GPU 时 128）、配色切全色相；切回杆时 N 若 >128 收回 100 |
| | 输出 | Grease Pencil / **图像**（一像素一个摆）/ 网格 + 几何节点（对照用） |
| | 求解器 | **自动**（能 import taichi 就用 GPU，否则 NumPy）/ **NumPy** / **Taichi**（强制，失败会报错） |
| | 子步数 | 每帧几个 RK4 子步 —— 唯一的「播放速度」旋钮：物理时间/帧 = dt × 子步 |
| 物理 | 重力 / 杆长 / 质量 | 无阻尼双摆的全部参数，改完下一帧就生效（不重建） |
| | 子步 dt | RK4 子步时长（缺省 0.005 s）。四阶格式很稳，画面再乱也别超过 0.02 |
| 外观 | 配色 | **全色相**（θ → 色轮一圈）/ **角速度**（\|dθ\| → 石青·赭石·朱砂）/ **相角**（½(1−cosθ)）/ **双色**（上摆一个固定色、下摆另一个） |
| | 角速度满标 | 角速度色带的满标（缺省 12 rad/s ≈ 2 圈/秒），不做逐帧自归一化 |
| | 上摆色 / 下摆色 | 双色档的两个取色器，缺省就是参考实现的 `#796BAF` / `#719C73` |
| | 笔半径 | 杆的半径（缺省 0.08，与参考实现一致）；整根杆等宽、两端圆头 |
| | 扣子倍数 | 扣子半径 / 杆半径，缺省 **5/8**（= 0.05/0.08，参考实现的配比） |

- **物理参数**：下一帧就生效，不重建；
- **外观参数**：当场重刷当前帧（不推进物理）；
- **阵列 / 初值 / 输出**：进签名，下一帧由 handler 自动重建（也可以手动点「重建」）。

**配色怎么映射**：上摆和下摆各取一路颜色，都是"自己那根杆"的状态 ——

| 档位 | 上摆 | 下摆 | 用在 |
|---|---|---|---|
| 全色相 | 色相 `½(θ1+θ2)` **+30°** | 色相 `½(θ1+θ2)` **−30°** | 相角是周期量，铺满色轮最自然；初值色带是 45° 斜纹，N 大时看分形 |
| 角速度 | `\|dθ1\|` | `\|dθ2\|` | 静止的冷、甩起来的烧红 |
| 相角 | `½(1−cosθ1)` | `½(1−cosθ2)` | 垂下去冷、举起来暖 |
| 双色 | 固定 `#796BAF` | 固定 `#719C73` | 纯线稿，两根杆一眼分得开（扣子跟下摆同色） |

色相那档的饱和度固定 0.9、明度 1.0，**只让色相走满一圈**（六段原色都在用），
这样"颜色流动"读起来是相角的连续变化，而不是明暗在闪。

**全色相档的色相取的是两根摆角的平均** `½(θ1+θ2)`：θ1 沿 X、θ2 沿 Z 等权，等值线正好是
**45° 斜纹**（只取 θ1 是竖条、只取 θ2 是横条）。杆画法在这个斜纹色相上各偏 ±30°
（两根杆差 60°，仍然一眼分得开；`_SPECTRUM_SPLIT` 改成 0 就是同色、0.25 就是互补）；
点阵画法一个像素只能一个颜色，直接用斜纹色相。

**扣子倍数的两个取值意味很不一样**（缺省 5/8 是照参考实现的配比）：
`< 1` 时扣子比杆细，会收进两根杆在关节处的圆头里，只在接缝外缘露一点；
`> 1` 时它才是一颗明显的铆钉，把上摆的端头"扣"住。面板会按当前值提示是哪一种。

读数：当前步数、角速度峰值、平均能量与**相对能量漂移**、每帧总耗时、积分 / 摊缓冲 /
写后端三段耗时、后端名、上次构建耗时。点「对照实测」会当场把 GP 与网格各刷 50 次，
把两个数字并排显示出来（就是下面那张表的来源）。

## 物理模型

标准理想双摆（无阻尼、无驱动），角度以向下为 0、逆时针为正：

```
Δ = θ1 − θ2,   D = 2m₁ + m₂ − m₂cos(2Δ)
θ̈1 = [ −g(2m₁+m₂)sinθ1 − m₂g·sin(θ1−2θ2) − 2sinΔ·m₂(dθ2²l₂ + dθ1²l₁cosΔ) ] / (l₁D)
θ̈2 = 2sinΔ·[ dθ1²l₁(m₁+m₂) + g(m₁+m₂)cosθ1 + dθ2²l₂m₂cosΔ ] / (l₂D)
```

- **积分是真正的 RK4**：`y' = f(y)` 的标准四阶公式，每子步 4 次向量求值。
  参考脚本（`.lab/double_pendulum.py`）那版把 k2/k3 的 θ 导数混进了 k1 的角加速度，
  只是"看起来像"四阶，能量守恒差得多；
- **能量守恒**（面板读数用它）：`T = ½(m₁+m₂)l₁²dθ1² + ½m₂l₂²dθ2² + m₂l₁l₂dθ1dθ2cosΔ`，
  `V = −(m₁+m₂)gl₁cosθ1 − m₂gl₂cosθ2`，`E = T + V`。实测 20 s 物理时间（dt=0.005，
  4000 子步）平均能量相对漂移 **−3.0e−6**（摆角平面）/ **−5.9e−5**（相空间切片，
  初角速度 ±9 rad/s）；缺省 120 帧后是 −3.8e−7。漂移只增不减是 RK4 的典型特征；
- **摆放**：参数 1（i）沿 X、参数 2（j）沿 Z，整体居中；杆永远在 XZ 平面里（Y = 0），
  所以正面正交相机看过去就是一张平面相图，没有任何透视缩短；
- **GPU 在哪、值不值**：1 万个摆彼此**完全独立**，正是 GPU 的形状 —— 但这一帧真正要算的
  只有 ~8 MFLOP，快不快全看"开销"而不是"算力"。NumPy 版一次加速度求值（1 万元素、
  numpy 2.5）实测 **437 µs**：6 次三角函数 ~163 µs + ~30 个逐元素算子（几乎每次都分配临时
  数组，普通乘法只要 1.8 µs/次），一帧 20 次就是 9 ms —— 这就是积分那 5~10 ms 的来源。
  所以面板给了**求解器**三档：自动 / NumPy / Taichi。Taichi 版把"RK4 的 4 段求值 + 5 个子步
  + 五笔点列"全塞进**一个 kernel**，每帧只回拷一次（1 万摆 800 KB），实测 N=100 从
  **8.2 ms（NumPy，122 fps）压到 3.4 ms（Taichi，292 fps）**。代价：可选依赖、
  f32 精度、第一次构建多 ~0.6 s（编译 kernel），以及小规模反而更慢（N=16 时 1.09 vs
  0.98 ms —— 回拷的固定开销比算的还多）。

**实测整帧墙钟**（Blender 5.2.2 后台，GP 输出 + 全色相，顺序播 40 帧平均；后台没有视口
重绘，真实播放要再加 ~5 ms）：

| N | 摆数 | **NumPy** | **Taichi** | 倍速 |
|---|---|---|---|---|
| 16 | 256 | 0.98 ms（1023 fps） | 1.09 ms（915 fps） | 0.9× |
| 32 | 1024 | 1.79 ms（559 fps） | **1.43 ms（700 fps）** | 1.3× |
| 48 | 2304 | 2.71 ms（369 fps） | **1.79 ms（560 fps）** | 1.5× |
| 100 | 10000 | 8.17 ms（122 fps） | **3.43 ms（292 fps）** | 2.4× |

N=100 时两档的分解：NumPy 积分 5.38 / 摊缓冲 1.94 / 写回 0.60 ms；Taichi 0.55~1.22 /
1.55 / 0.55 ms。**GPU 只吃积分**，摊缓冲（配色 + 点重排）和写回仍在 CPU —— 这就是为什么
1 万摆不是"20 倍"而是 2.4 倍；再往上（10 万摆，积分 >50 ms）差距才会拉到 10 倍量级。

缺省一帧走 5 个子步 × 0.005 s = **0.025 s 物理时间**，24 fps 下就是 0.6 倍实时（慢放）。
想快点播就加「子步数」，想更稳就减「dt」——两者都只影响这一帧走多少，不改物理。

## GP 与网格的同步效率对比

问题：**把原生网格换成 Grease Pencil 笔划，还能同样高效地同步顶点吗？**
答案是能，而且规模上去以后快一个数量级。下表的数字来自同一台机器（Blender 5.2.2 LTS /
Windows / Python 3.13）、同一份缓冲、只量 `refresh()` 的调用耗时
（`sim_pendulum.benchmark`，50 次平均，剔除首次建属性）：

| N | 摆数 | 笔划点 / 顶点 | 同步 float32 | **GP 写入** | **网格写入** | 倍数 |
|---|---|---|---|---|---|---|
| 16 | 256 | 1 280 | 17 920 | **0.026 ms** | 0.110 ms | 4.3× |
| 32 | 1024 | 5 120 | 71 680 | **0.029 ms** | 0.393 ms | 13.8× |
| 48 | 2304 | 11 520 | 161 280 | **0.034 ms** | 0.865 ms | 25.6× |

两条后端写的是**完全同一份数据**（都是 ``5S`` 个点 × 位置 3 + 半径 1 + 颜色 4，外加 6 个
标量），所以差别全在写回路径上：

- **GP 是纯 memcpy**：`drawing.attributes[...].data.foreach_set(...)` 之后
  `tag_positions_changed()` 只**标脏**，重算推迟到 depsgraph。48² 时 161 280 个 float32
  （630 KB）只花 0.034 ms ≈ **18 GB/s**，而且几乎与规模无关（小规模时是 5~6 µs/条的调用开销）；
- **网格慢在属性写入本身**：同样一份数据要 0.865 ms ≈ 0.7 GB/s，慢 26 倍。顺手量过
  `mesh.update()` 只有 0.0012 ms，所以瓶颈**不是**重算法线/包围盒，就是
  `foreach_set` 走网格属性域的那条路比 GP 的 drawing 属性质慢一个数量级；
- **逐点半径 / 颜色在 GP 里是天生的**：两者都是 POINT 域，一个点一份；网格的"边"没有属性，
  想让一根杆一个颜色就得"整条边同色"（顶点复制），参考实现
  （`.lab/double_pendulum.py`）正是 6 顶点 / 3 条边、``48`` 个 float32/摆——比这里的
  ``5S`` 方案多 20%，而且它只建了网格和属性、没有配几何节点，裸边在 Blender 里根本不渲染。

整帧墙钟（含 depsgraph 求值，顺序播 40 帧平均，NumPy 求解器，GP 输出）：

| N | 摆数 | 积分 | 摊缓冲 | 写后端 | **整帧** |
|---|---|---|---|---|---|
| 16 | 256 | 0.58 ms | 0.14 ms | 0.04 ms | **0.98 ms** |
| 32 | 1024 | 1.09 | 0.31 | 0.18 | **1.79 ms** |
| 48 | 2304 | 1.76 | 0.49 | 0.56 | **2.71 ms** |
| 100 | 10000 | 5.38 | 1.94 | 0.60 | **8.17 ms** |

（同一台机器上换成 Taichi 求解器：0.98→1.09 / 1.79→1.43 / 2.71→1.79 / 8.17→3.43 ms，
见「物理模型」的求解器对比表。网格输出那一路的整帧是 GP 的 1.5~1.8 倍。）

也就是说：**整帧的大头是积分**（逐元素算子 + 三角函数，见「物理模型」里的分解），
GP 的写回在 N=48 时只占整帧的 20%、N=100 时 7%。用 GP 不但没变慢，还把网格那条路上
40% 的整帧时间省掉了（以及 8 倍多的面数：GN 圆管在 48² 时是 11.5 万面）。

另外一个实际问题：网格要画出"线"就得挂几何节点扫管，而 GP 本身就是线（两端圆头、
一条笔划一个颜色都是原生行为）。这个插件的 `mesh.py` 为了把管半径接上 `radius` 属性踩了
三个 5.2 的坑（都不报错，只是画面上什么都没有）：

1. 节点组必须 `group.is_modifier = True`，否则 NODES 修改器不参与求值、原样透传源网格；
2. `Curve to Mesh` 的 `Profile Curve` 必须接一个剖面（这里用 `Curve Primitive Circle`，
   半径 1、6 段），空着时输出只是骨架折线（N 点 0 面）；
3. 粗细必须喂 `Curve to Mesh` 的 `Scale`，**不能**指望曲线点半径 —— `Set Curve Radius`
   改的点半径只影响"曲线对象自身的倒角渲染"，`Curve to Mesh` 根本不读（实测剖面半径 1 +
   曲线半径 0.5 → 管子半径仍是 1）。

颜色也有两条坑：几何节点扫出来的求值网格上 `color_attributes.active_color_index == -1`，
所以 `Color Attribute` 节点留空 `layer_name` 的写法（本仓库其它网格插件用的）在这里取不到
颜色；而属性名若叫 `color` / `vertex_color`，Cycles 又会当成自己的标准顶点色名取到空值。
最终方案：属性叫 **`ink_color`**，材质用 `ShaderNodeAttribute`（`attribute_type='GEOMETRY'`）
按名字直取 —— EEVEE 与 Cycles 都验过，颜色一致。

## 数据接口

GP 对象（`Sim Pendulum`）的 drawing 上的属性，几何节点 / 着色器可以直接按名字取：

| 属性 | 类型 / 域 | 含义 |
|---|---|---|
| `position` | FLOAT_VECTOR / POINT | 世界坐标。一个摆 5 个点：`0-1` 下摆（关节 → 摆锤）、`2-3` 上摆（悬挂点 → 关节）、`4` 扣子（关节） |
| `radius` | FLOAT / POINT | 逐点半径：四根杆端 = 笔半径，扣子 = 笔半径 × 扣子倍数 |
| `vertex_color` | FLOAT_COLOR / POINT | 线性 RGBA：下摆两点 + 扣子同色，上摆两点另一种颜色 |
| `theta1` / `theta2` | FLOAT / POINT | 两个摆角 [rad] |
| `speed` | FLOAT / POINT | 角速度大小 `√(dθ1²+dθ2²)` [rad/s] |
| `speed_upper` / `speed_lower` | FLOAT / POINT | 两根杆各自的角速度 `\|dθ1\|` / `\|dθ2\|` |
| `energy` | FLOAT / POINT | 该摆的总机械能 [J] |

网格后端（`Sim Pendulum Mesh`）属性一一对应，只有颜色叫 **`ink_color`**（Cycles 的坑，
见上一节）。网格的顶点 4（扣子）是孤立顶点：留着只为让两边写回的数据量严格相等，
`Mesh to Curve` 会丢掉它，所以网格后端没有扣子。

## 模块

```

strokes.py      场 → 笔划缓冲：三笔点列 / 逐点半径 / 逐点颜色 / 标量  （不 import bpy）

mesh.py         网格后端：5 顶点 2 边 + 几何节点扫成圆管（对照用）
sim.py          frame_change_pre handler：推进 → 摊缓冲 → 写后端，并分三段计时
```

## 规模：一像素一个双摆（点阵画法）

杆画法一笔一个摆、一个摆三个点，几万条笔划就到头了；想再往上只能**一个摆一个像素**：
不建笔划、不建对象、不建材质，直接算一张 `N×N` 的图，`image.pixels.foreach_set` 一次写进去
（就是 `.lab/taichi_image.py` 那套）。看结果按 **Shift+F10** 开一个图像编辑器，或者点面板上的
「在图像编辑器里查看」；「构建」时会顺手把图推到已经打开的 Image Editor 里。

实测（Taichi 求解器 + 图像后端，后台播放 30 帧平均）：

| N | 摆数 = 像素数 | 整帧 | fps | 其中积分 | 摊缓冲 | 写图像 |
|---|---|---|---|---|---|---|
| 256 | 65 536 | **3.3 ms** | 299 | 1.0 | 1.5 | 0.3 |
| 512 | 262 144 | **13.2 ms** | 76 | 2.4 | 6.0 | 2.2 |
| 1000 | 1 000 000 | 49.3 ms | 20 | 7.8 | 22.6 | 6.1 |

同规模下 GP 单点笔划那版是 5.0 / 17.6 / 72.7 ms —— 图像后端省掉了笔划层（100 万条笔划的
建、写、画），渲染时只是一张贴图；顺带把渲染分辨率钉成 `N×N`，**一个渲染像素正好对应一个
双摆**，出图不用再算比例。

结论还是那句：**物理不是瓶颈**。单看积分 kernel，100 万摆 × 5 子步只要 **0.13 ms**
（4080 SUPER 上量过，4 段 RK4 + 5 子步全在一个 kernel 里）。卡住 1M 的是搬运与摊平：

* Taichi→NumPy 回拷 ≈ 2 GB/s：1M 摆的状态 16 MB ≈ 7.8 ms（点列那 60 MB 已跳过）；
* 摊缓冲（Python）22.6 ms：1M 个像素的颜色（已换成"量化 256 级色轮 + 查表"）加半径；
* `image.pixels.foreach_set` 16 MB ≈ 6 ms（也是 ~2.5 GB/s）。

再快一步的路子很清楚（还没做）：把色轮和 RGBA 写回全搬进 kernel，Python 侧只做一次
`foreach_set` —— 摊缓冲会降到 ~0（只剩回拷的 16 MB），1M 预计 **~15 ms ≈ 65 fps**。
这次改动会引入一份 Taichi 版的配色逻辑（只支持全色相档），所以先停在现在这版。

## 取景

阵列是正方形的，画面也就用近正方形（宽高比 1.09）。`ortho_scale` 作用在**长边**上，所以取景按

```
extent = (N−1)·间距 + 2·(l1 + l2)      # 摆可以甩到水平，所以两边各留一个 reach
span   = max(extent, extent × 宽高比) × 1.06
```

算 —— 只按宽度算的话上下两排会被切出画面。相机摆正前方（沿 +Y 看，`rotation_euler = (π/2, 0, 0)`），
不做倾斜：斜视只会让上下两排的摆互相压住，相图就散了。

**分辨率跟着 N 走**：每世界单位 26 px，长边封顶 3200 px。所以 N=16 是 1200×1100，
N=48 是 3200×2940。不这么做的话，100² 铺进 1200 px 时一根杆只有半个像素宽，
颜色全被背景吃掉，分形图案也就看不见了。

## 与参考实现的差别

参考实现是 `.lab/double_pendulum.py`（Taichi kernel + 6 顶点 / 3 边网格 + `vertex_color` /
`radius` 属性）。物理方程照搬，差别在工程结构：

| | 参考脚本 | 本扩展 |
|---|---|---|
| 组织方式 | 单脚本（Taichi kernel 与 Blender 集成混在一起） | 扩展包：算法层与 Blender 层分开，可单独测试 |
| 数值 | f64 Taichi kernel，RK4 的 k2/k3 组装有误 | 标准 RK4：NumPy 走 f64、Taichi 走 f32（能量漂移 −2.3e−6 / 20 s） |
| 后端 | 只有 Taichi，缺依赖就跑不起来 | NumPy（零依赖，缺省回退）+ 可选 Taichi，面板里切 |
| 结果落到场景 | 网格 + 属性，**没有几何节点**（裸边不渲染） | GP 三笔（杆等宽圆头 + 扣子）或网格 + GN 圆管（面板可切） |
| 逐点半径 | 建了 `radius` 属性但没有节点消费 | GP 直接吃 `radius`；网格走 `Curve to Mesh` 的 `Scale` |
| 杆的形状 | 6 顶点 / 3 边（含一条零长度的"扣子边"） | 5 点 / 3 笔：`2+2+1`，一根杆一段、扣子单独一个点 |
| 视觉 | 两根杆两色，扣子与上摆同色（`c1`） | 两根杆两色，**扣子与下摆同色**（按你的描述） |
| 相空间 | 固定 θ1–θ2 网格 | θ1–θ2 与 θ1–dθ1 两档初值 |
| 配色 | 两个固定色（`#796BAF` / `#719C73`） | 全色相（相角 → 色轮）/ 角速度 / 相角 / **双色**（缺省就是那两个色），两路各管一根杆 |
| 场景 | 无 | 世界底色 + 正面正交相机 + Standard 色彩 + 随 N 变化的分辨率 |
| 计时 | 无 | 每帧总耗时 / 积分 / 摊缓冲 / 写后端 + 能量漂移 |

## 局限与下一步

- **没有烘焙**：动画靠 `frame_change_pre` 实时算，渲染动画时帧要按顺序走（Blender 默认如此），
  **回退会重置**整个阵列（`target < 当前帧` 就从初始阵列重算）。1 万个摆回退 100 帧约 1.2 s；
- **摆之间没有碰撞**：乱起来以后线会互相穿过。线稿的好处正在这里 —— 穿模不显眼，但如果要
  "实"的管状轮廓，得走网格后端（GN 扫管）；
- **笔划数量**：杆画法是 3N²（100² = 3 万条）；点阵画法走图像，**一条笔划都没有**
  （512² = 26 万像素、1000² = 100 万像素一张图）；
- **GPU 只加速积分**：摊缓冲（配色）和写回仍在 Python。1 万摆时 GPU 只快 2.4 倍；
  100 万像素时积分只占整帧 16%（7.8 / 49.3 ms）—— 大 `N` 的瓶颈已经是 CPU 侧配色和
  Taichi 回拷，这也是下一步要搬到 kernel 里的东西；
- **每个摆只有 3 条笔划**：看不出一条连续轨迹。想要"相图拖尾"就得改成环形缓冲的长笔划
  （每条笔划 M 个点、逐帧整体滚动），同步量按 M 线性增长 —— 那时 GP 的优势更明显
  （网格的顶点数要多 1.33~2 倍才能按段拆色）；
- **没有驱动 / 关键帧**：参数改动实时生效，但如果要在渲染农场里出片，得自己把每帧的
  `position` 烘焙成形状键或动画属性。
